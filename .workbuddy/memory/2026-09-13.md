## 排查 GitHub Actions 打包失败（poker_gto_android）

**用户反馈**：「github 的 actions 失败了」。

**仓库**：`https://github.com/lizanle521/GTO.git`（**私有**）。私有仓库无法匿名读 Actions

### 定位到的根因（高置信）

**`buildozer.spec` 缺少 `android.accept_sdk_license = True`。**

证据来自 buildozer 源码：

```python
# buildozer/targets/android.py :: _android_update_sdk()
auto_accept_license = self.buildozer.config.getboolean(
    'app', 'android.accept_sdk_license', fallback=False)   # ← 默认 False

if auto_accept_license:
    kwargs["return_child"] = True
else:
    kwargs['show_output'] = True
```

且 buildozer 默认 spec 模板里该行是注释状态：

```
# android.accept_sdk_license = False
```

默认 False 时 buildozer 会以交互方式询问是否接受 SDK 许可证；GitHub Actions 无终端可输入，
SDK 组件装不上，构建在下载 SDK 阶段就挂，典型报错：

```
Failed to install the following Android SDK packages as some licences have not been accepted
```

配置里已补上该行，并加了注释说明「不要删」。

### 我这边的第二个错误（自己造成的）

旧 workflow 里写的是：

```bash
buildozer -v android debug 2>&1 | tail -n 200
```

**管道会让退出码变成 `tail` 的（永远 0）**，所以即使 buildozer 失败，这一步仍显示绿色，
真实错误被吞掉，只在最后的「上传 APK」步骤报 `if-no-files-found: error`，误导性很强。
已本地实测复现：`bash -c "exit 7" | tail -n 5` 的整条管道退出码确实是 0。

正确写法（已采用）：

```bash
set +e
yes | buildozer -v android debug 2>&1 | tee build.log
STATUS=${PIPESTATUS[1]}     # [0]=yes [1]=buildozer [2]=tee
exit "$STATUS"
```

实测注意：`yes` 在中途会收到 SIGPIPE 退出（141），**所以这里不能用 `set -o pipefail`**，
否则构建成功时反而会误判为失败。已用本地脚本验证 `PIPESTATUS[1]` 在成功/失败两条路径取值都正确。

## 09:10 架构确认：识别与决策分离（并定位契约缺口）

用户问「是模型直接给 GTO 建议，还是模型只识别、本地算」。回答前通读了
`recognizer.py` / `realtime.py` / `main.py:_make_recommendation`，确认现状：

**当前是"模型只识别 + 本地决策"**（即用户说的方案 1）：
摄像头帧 → FrameAnalyzer 变化检测节流 → 抽帧 base64 → 云端 VLM →
CARD_PROMPT 要求的 JSON → parse_cards 归一化 → 本地
`ranges.get_open_action()`（翻前）/ `poker_core.evaluate_best`
+ `analyze_draws` + `postflop_advice`（翻后）。

`recognizer.CARD_PROMPT` 当前的输出契约只有 5 个字段：
`hole_cards / board_cards / hero_position / confidence / notes`。

**记录一个明确的缺口**：这套字段不足以支撑真正的 GTO 决策，只能支撑
"翻前开池/弃牌 + 翻后按牌力与听牌给方向性建议"。要往真 GTO 走，
prompt 必须补充这些决策输入（模型只需"读出来"，不需要"想"）：
有效筹码深度（bb）、入池人数/桌型、hero 面对的动作（现在默认无人入池，
只能算 RFI）、底池大小、对手下注额（算底池赔率）、街。

**设计纪律（三条，后续改动都要守）**：
1. 模型只做"画面 → 结构化事实"的翻译，绝不让它输出打法建议；
2. 输出必须结构化且可校验（`parse_cards` 已在做正则提取 + 字段归一化）；
3. 必须允许模型说"不知道"（`??` 占位 + `confidence` 字段），否则它会被逼着编。

**若将来要让模型参与"思考"**，正确位置是**解释层**（本地算完再把建议翻译成人话）
或**复盘层**，这两处对延迟不敏感，不是实时决策层。

## 14:10 定位并修复云端构建失败（android.features）

用户报「github build 失败」。**这次仓库已转为 public**，API 匿名可读（`api.github.com/repos/...` 返回 200），
终于拿到了真实日志。

### 拿日志的正确姿势（私有仓库也适用）

1. `GET /repos/{o}/{r}/actions/runs` —— 列 run，拿 id
2. `GET /repos/{o}/{r}/actions/runs/{id}/jobs` —— 看哪个 step 挂了
3. `GET /repos/{o}/{r}/actions/jobs/{job_id}/logs` —— **会 302 跳到 Azure 存储**。
   urllib/curl 默认会把 `Authorization` 头一起带过去，而那个 URL 自带 SAS 签名，
   多出来的 GitHub token 会让 Azure 报 `InvalidAuthenticationInfo`。
   **必须两跳**：第一跳带 token 取 `Location`，第二跳不带 token 取内容。
4. artifact 同理（`/actions/artifacts/{id}/zip`）。体积比 job 日志小得多
   （build.log 压缩后 291 KB vs job 日志几十 MB），**优先拉 artifact**。
5. 私有仓库要认证时，本机凭据可用 `git credential fill` 取（
   `printf 'protocol=https\nhost=github.com\n\n' | git credential fill`）。

### 根因

```
toolchain.py: error: unrecognized arguments: --feature android.hardware.camera
```

buildozer 源码 `buildozer/targets/android.py:1149`：

```python
features = config.getlist('app', 'android.features', [])
for feature in features:
    build_cmd += [("--feature", feature)]     # ← 写死的 --feature（单数）
```

而 p4a v2024.01.21 的 `apk` 命令**根本没有 `--feature` 参数**（只有 `--permission`）。
即 **buildozer 的 `android.features` 对这个版本的 p4a 完全不可用**，是 buildozer 自身的缺陷。

**最坑的是失败位置**：构建跑到 15 分 46 秒，Python / numpy / cython / pyjnius 全部编译完，
只在最后组装 apk 时才被 argparse 拦下。看到"跑了很久最后才报错"就要往**参数错误**上想，
不要怀疑环境/磁盘/NDK。

### 顺带查出的第二个静默 bug

`buildozer/targets/android.py:1245`：

```python
orientation = config.getlist('app', 'orientation', ['landscape'])   # ← 读的是 orientation
```

spec 里写的是 `android.orientation = portrait`，**被静默忽略**，实际用默认 `landscape`。
不报任何错，只能靠翻构建日志里的 `--orientation` 才发现。

抓 `buildozer/targets/android.py` + `__init__.py`，正则
`config\.get\w*\(\s*'app'\s*,\s*'([^']+)'`，与 spec 里的 key 求差集。
（注意：`source.*` / `version` / `log_level` 由 buildozer 核心读取，不在 android.py 里，

### skill 在两轮实测中又修掉三个问题

1. **ANSI 颜色码让锚定正则静默失效**（最隐蔽）
   buildozer 输出 `\x1b[0m\x1b[1;31m# Command failed: (...`，
   终端里显示正常，字节上行首是 ESC → `^#\s*Command failed` 匹配 **0 行**，
   去掉锚点才匹配 1 行。修法：读取时统一剥离 ANSI 码。
2. **CPython 标准库语法噪音**：p4a 对 `Lib/` 全量 compileall，`Lib/test/` 下刻意写错的
   语法用例（`future feature X is not defined` / `Missing parentheses in call to 'print'` /
   `invalid character '€'` 等 8 种）会命中 `SyntaxError` 强信号。一次实测里最初 8 条
   强信号命中**全部**是这类噪音。修法：内置 `NOISE_PATTERN`（实测一次过滤 17 条）。
3. 新增 **`# Command failed` 锚点段**：直接给出失败命令，并在窗口内挑出"最像根因的行"
   （排除 argparse 的 usage 帮助文本）。实测效果：
   ```
   >>> 窗口内最像根因的行：
    35242| toolchain.py: error: unrecognized arguments: --feature android.hardware.camera
   ```
   一行命中，正好是先前需要人工筛 1100 条噪音才找到的那行。

**再次印证**：这三条全是**只有拿真实日志跑才能发现**的问题。写完脚本不实测 = 没写。

### 一个容易踩的认知

**concurrency 的 cancel-in-progress 不会取消"在它之前创建的" run**。
本次实测：新 run `34744110702` 带上 concurrency 启动后，旧的 `34744033853`
仍是 in_progress。原因是旧 run 由**没有 concurrency 段的旧 workflow** 创建，
不属于任何 group，自然不匹配。**该配置只对生效之后的新 run 起作用**。

### 另一个权限事实

取消 run 的 API（`POST /actions/runs/{id}/cancel`）需要 `actions:write`，
而本机 git 凭据（`git credential fill`）只有仓库读写权限，
调用返回 **401 Bad credentials**。想取消得去网页点，或用 `gh`（本机没装）。
