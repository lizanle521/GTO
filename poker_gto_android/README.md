# GTO 助手（安卓 App）

一个**德州扑克 GTO 学习工具**，安卓端。摄像头拍下牌面 → AI 识别 → 给出基于 GTO 范围表的行动建议；同时内置刷题训练模式。

> **用途声明**：本工具面向**学习与训练**。请勿用于真实牌局的实时决策——在正规赛事中使用实时辅助（RTA）属作弊行为，会被禁赛。识别结果仅供参考，实际决策请自行判断。

---

## 一、这个 App 能做什么

| 功能 | 说明 | 是否需要联网 |
|---|---|---|
| **实时牌面识别** | 摄像头对着牌桌，自动抽帧识别手牌/公共牌/位置/筹码深度/底池 | 需要（调 AI 接口） |
| **GTO 行动推荐** | **翻前与翻后**都给出行动建议，附胜率与依据 | **不需要**（本地计算） |
| **刷题训练** | 三个模块出题：翻前开池、翻前对抗加注、翻后决策 | 不需要 |
| **成绩统计** | 正确率、分模块正确率、历史记录 | 不需要 |

**关键设计**：AI **只负责"读"**——把画面翻译成一份结构化的事实清单（牌、位置、人数、筹码深度、底池、要跟多少）。**所有打法判断都在本地完成**：翻前查内置范围表，翻后跑蒙特卡洛算胜率再比底池赔率。所以识别与决策是两条完全独立的链路，AI 说得对不对，都不会影响决策规则的确定性；反过来，决策规则改了也不需要动 AI。

这样切分有两个实际好处：

- **可校验**：AI 的输出是一堆可以被检查的事实（牌只有 52 张，能查重、能验合法性），错了一眼就能看出来；而"建议加注"这种结论是无法校验的。把不确定性关在一个窄接口里，比让它渗进结论里强得多。
- **离线可用、零成本**：不填 API Key 也完全能刷题，识别结果也能手动修正。牌读错了不至于全盘皆输，改一下重算就行。

## 六、技术实现要点

### 实时识别的成本控制

摄像头不能每帧都送 AI（费用爆炸、也没必要）。`realtime.py` 做了两层过滤：

1. **变化检测**：把画面降采样成 32×32 灰度图，与上一帧做差分。变化率低于阈值（默认 8%）说明画面没变，直接跳过。
   - 这里阈值调得很低，因为**发牌只改变画面 5%-15% 的区域**，阈值太糙会漏掉。
2. **节流**：两次识别之间至少间隔 `capture_interval` 秒（默认 3 秒）。

只有"画面确实变了" **且** "距上次识别够久了"，才真正调用 AI。识别统计在实时识别页底部实时显示。

### 识别与决策的分工

**AI 只回答"发生了什么"，不回答"该怎么办"。** `recognizer.py` 让模型吐出的是一份固定格式的事实清单：

```json
{
  "street": "flop", "hole_cards": ["As","Kh"], "board_cards": ["Qs","Jh","2c"],
  "hero_position": "BTN", "num_players": 6,
  "effective_stack_bb": 100, "pot_bb": 6.5, "bet_to_call_bb": 2,
  "num_raisers": 1, "num_limpers": 0, "confidence": "high"
}
```

每个字段都是**可校验**的：牌面查重、验合法（同张牌不能出现两次）；数字有合理区间（人数 2-10、筹码深度 1-1000bb）。**看不出来的一律填 `null`，不许猜**——猜出来的数字比 null 更糟，因为它看起来像是真的。prompt 里明确写了这条。

解析层拿到结果后会做三件事：

1. **抠数字**：`"$100"` / `"6 人"` 这种脏值也能读出数值，不因为格式问题整条丢弃。
2. **统一"街"的口径**：以**公共牌张数**为准（0 张=翻前、3 张=翻牌、4 张=转牌、5 张=河牌），模型自报的 street 只作参考，冲突时记一条警告。这样不会出现"模型说是翻牌、但读出来 5 张公共牌"这种自相矛盾还照算的情况。
3. **缺失降级**：关键字段（人数、筹码深度、底池、要跟多少）读不到就给 `None`，**不抛错**，交给决策层按兜底假设处理，并在界面上把假设原样列出来让用户确认。

### 翻前决策

`decision.py` 按场景分流，而不是"一手牌一个答案"——同一手牌在不同场景下结论完全不同：

| 场景 | 处理方式 |
|---|---|
| 无人入池，轮到我开池 | 查位置的**开池范围表**（UTG 约 10% → BTN 约 46%） |
| 面对一个开池加注 | 查**3bet 范围** → 在范围内加注，否则查**跟注范围** → 否则弃牌 |
| 面对 3bet | 查**4bet 范围** → 加注，否则查**对抗 3bet 的跟注范围** → 否则弃牌 |
| 前面有人 limp | **隔离加注**（用收紧后的开池范围加一个大尺度） |
| 大盲位置无人加注 | 按起手牌强度排名，前段加注、其余过牌看翻牌 |

**筹码深度会调整范围宽度**：短筹码（<40bb）时，那些需要靠翻后操作兑现价值的边缘同花连张会被逐步砍掉（60bb 保留 100%、30bb 保留 80%、20bb 保留 70%），因为它们没空间玩了；而高对、强张不受影响。

### 翻后决策

翻后先算胜率，再比底池赔率。`postflop_advice()` 的判断顺序很关键，写错会导致建议和牌力不符：

1. **顺子及以上** → 下大注（约 3/4 池）
2. **两对/三条/葫芦/四条** → 下大注建池
3. **超对** → 下注（注意：超对是**成牌**，不是听牌）
4. **强听牌**（同花听牌 或 两头顺）→ 半诈唬
5. **弱听牌**（卡顺）→ 小注或过牌
6. **顶对** → 按牌面高低决定下注尺度
7. **弱牌** → 过牌

**面对下注时另走一条路**：算出当前胜率，和 `底池赔率(bet, pot_before) = bet / (pot_before + 2*bet)` 比较。胜率够就跟（或加注），不够就弃牌。

这里有个必须说清楚的坑：**胜率是对"随机范围"算出来的，比真实对手范围乐观**（对手不会用任意两张牌加注）。所以比较时额外留了 5 个百分点的安全余量，胜率要超出底池赔率要求 5% 以上才跟注。宁可少跟一手边缘牌，也不要因为高估胜率而长期送钱。

还有一个概念差别容易搞混：本项目的 `estimate_equity()` 返回的是**纯胜率**（平局单独统计，不折半计入）。而常被引用的"72o 有 34.6% 胜率"是**含平局折半**的 equity，两者差值正好是平局率的一半。遇到数字对不上时先分清是哪一个，别急着改代码。

### 听牌识别逻辑

区分**两头顺**和**卡顺**的方法：数补牌点的个数。

- **AK 在 QJ2**：只有 T 能补（TJQKA）→ 1 个补牌点 → **卡顺**（4 张出路）
- **98 在 T72**：补 J 成 789TJ、补 6 成 6789T → 2 个补牌点 → **两头顺**（8 张出路）

注意不能用"缺口是否在窗口两端"来判断——AKQJ 缺 T，T 在窗口端点，但它只能成一条顺子，是卡顺。

### 范围表的一致性

`ranges.py` 用紧凑写法定义范围（`"A5s-A2s"`、`"77+"`、`"KTs+:0.5"`），加载时自动展开并**校验**：同一手牌在 3bet 范围和跟注范围内的权重之和不能超过 100%。

如果数据写冲突了，`reconcile_ranges()` 会自动从跟注范围里扣掉 3bet 已占的权重，从根本上杜绝"同一手牌既 100% 3bet 又 100% 跟注"这种矛盾。

## 七、已知限制

1. **打包限制**：Buildozer 不支持 Windows，必须走 WSL2 / 云构建 / Linux。
2. **apk 体积**：Python 打包的 apk 约 40-60 MB（含 Python 解释器和 Kivy），比原生 App 大不少。
3. **启动速度**：首次启动需要几秒（解压 Python 运行时），比原生慢。
4. **摄像头**：Kivy 的 `Camera` 在部分安卓机型上兼容性一般，可能出现预览比例不对或启动慢。识别是"拍一帧送去分析"，不是连续视频流分析。
5. **识别准确率**：牌面识别受光线、角度、遮挡影响，可能出错。**所有识别结果都要人工校对**——GTO 推荐对牌面错误零容忍，牌读错一步，建议就全错。
6. **后台保活**：安卓会杀后台进程，切出去再回来可能需要重新开摄像头。
